03 Authoring · Timeline

Timeline Editor Backend

A full timeline backend — tracks, events, clips and markers with transport control — that the script compiler fills automatically. Effects start and stop by themselves when events fire.

Concepts

ConceptWhat it is
TrackA named lane with a type (effect, camera, post, audio, animation, event) and a mute flag.
EventA scheduled command bundle with a start time, optional duration, optional repeat (loopEvery), and an owning clip. This is what every at block becomes.
ClipA named region that groups events; offsetting the clip moves all of its events together.
MarkerA named cue point at a time — for scrubbing and rehearsal navigation.
KeyframesOwned by the AnimationSystem; the timeline starts and stops the animations.

Transport

Everything the keyboard controls maps to these operations. All of them are scriptable (speed, loop, jump commands) as well as key-driven.

▶

play / pause / toggle

Advance the clock; events fire as their times are crossed.

⏭

seek / jump

Move to an absolute time. Events do not re-fire on a seek — the fire boundary re-arms so nothing replays unless genuinely re-crossed.

↻

loop

Whole-show or section range looping.

±

speed

Scale the clock rate (timescale ramps are great for slow-mo moments).

Event firing semantics

Events stay sorted. Each frame, update(dt) returns every event whose time fell inside the crossed window, so each fires exactly once regardless of frame rate. Scrubbing backwards re-arms the boundary — a deliberate choice for live cueing. Fired events are handed out as stable copies via fired() / consumeFired(), so the director can safely react while the editor keeps updating.

JSON format

Timelines round-trip through JSON (data/timelines/*.json), loaded by the asset manager's timeline kind. Example from the bundled beat_map.json:

data/timelines/beat_map.jsonjson
{
  "duration": 125.0,
  "tracks": [
    { "name": "visuals", "type": "effect" },
    { "name": "camera",  "type": "camera" },
    { "name": "post",    "type": "post" }
  ],
  "events": [
    {
      "name": "intro",
      "time": 0.0,
      "duration": 0.0,
      "track": 0,
      "cmds": [
        { "name": "camera", "args": ["IntroCam"], "opts": { "rig": "drift", "pos": [0, 0, 2.4] } },
        { "name": "show",   "args": ["intro"],    "opts": {} }
      ]
    },
    { "name": "preset-cinematic", "time": 26.7, "track": 2,
      "cmds": [ { "name": "post", "args": ["preset", "cinematic"], "opts": {} } ] }
  ],
  "markers": [
    { "name": "Awakening", "time": 0.0 },
    { "name": "Nave",      "time": 13.3 }
  ],
  "clips": [
    { "name": "first-act", "start": 0.0, "end": 40.0, "track": 0 },
    { "name": "climax",    "start": 77.8, "end": 102.2, "track": 0 }
  ]
}
Tip

You rarely write these by hand — the script compiler produces them. But the format is public, so a timeline editor UI or a DAW export can generate a show directly.

From script to events

The ScriptEngine walks the parsed script and produces:

  • one TimelineEvent per top-level at block (absolute time);
  • scene-relative at sub-blocks offset by the scene's start time;
  • a SceneSection schedule (start/end per scene) from bars × BPM or explicit durations.
