Assets & Live Reload

A centralized asset manager with caching, reference counting, unload and reload. Every kind of content the demo needs is a file — and every file hot-reloads while the show runs.

Data layout

The runtime data root (data/ by default, overridable via NULLSECTOR_DATA_DIR) organizes content by kind:

data/ — the whole demo, as filestree
data/
├── demo.nsd            # the show: scenes, cues, rigs, animations
├── post/               # post-processing presets (JSON)
│   ├── cinematic.json  # bloom + grade + vignette + fxaa
│   ├── vhs.json        # chromatic + scanlines + grain + pixelate
│   └── clean.json
├── shadertoy/          # imported Shadertoy shaders
│   ├── plasma.glsl
│   └── tunnel_warp.glsl
├── models/             # OBJ meshes (terrain.obj, gem.obj …)
├── materials/          # PBR materials (chrome.json, neon.json …)
├── scenes/             # scene-graph JSON (lightbox.json …)
├── timelines/          # timeline JSON (beat_map.json …)
├── textures/           # PNG/JPEG sprites
└── plugins/            # optional effect plugins (.dll/.so)

Asset kinds

KindLoaderReload swaps
texturestb_image → GPU textureRe-uploads pixels.
modelOBJ importer → index buffersRe-imports geometry.
materialJSON → PBR materialRe-parses params.
sceneJSON → SceneGraphRebuilds the graph.
timelineJSON → TimelineEditorRebuilds tracks/events.
scriptText → ScriptEngineRe-parses, rebuilds events.
shaderShaderManager (tracks source)Recompiles program.

Handles are opaque; each loader returns a heap object its free function deletes. Reload functions swap the object in place and bump a version counter so renderers rebind — never a stale pointer, never a restart.

Reference counting

Assets are cached by path. Acquire bumps the refcount and returns the cached handle; release drops it; unreferenced assets are eligible for unload. In practice the director acquires once per named asset (sprites, models, materials) — loading the same texture every frame is both wasteful and a refcount leak, so keep acquisitions at setup time.

Live reload

A polling FileWatcher watches the script and the content directories. Each frame the director asks what changed and reloads exactly that:

File changedWhat happens
demo.nsd (or F2)Re-parse, rebuild timeline events + section schedule, restart cleanly.
*.frag / *.vertRecompile via ShaderManager; active effects pick it up next frame.
Shadertoy .glslImporter re-parses and rebuilds all passes.
texture / model / materialReload in place, version bump.
Workflow

This is the entire point: write a shader, save, watch it go live; tweak a camera rig, save, press F2. Iteration speed is the demoscene superpower, and here it costs nothing.

Failure modes

A load that fails is not terminal: the entry stays registered and reloadDirty() retries the loader, so an asset dropped in after the show started is picked up live. A deleted file fails loudly once (previous version kept, [ASSET] warns) and recovers automatically when the file comes back. Paths are compared canonically (separator-agnostic), so watcher-reported and app-acquired paths always match — the framework test suite locks this chain in.

Models & materials

The OBJ importer (src/app/model.cpp) builds indexed buffers with positions, normals, UVs and computed tangents; a forward-lit PBR-ish shader consumes them. Materials are JSON — base color, metallic, roughness, AO, emission, opacity:

data/materials/chrome.jsonjson
{
  "name": "chrome",
  "baseColor": [0.85, 0.9, 1.0, 1.0],
  "metallic": 1.0,
  "roughness": 0.08,
  "ao": 1.0,
  "emission": [0.0, 0.0, 0.0],
  "opacity": 1.0
}

Scene-graph mesh nodes reference models and materials by name; the director binds the actual Material at draw time, so swapping a material file restyles a model with zero script changes.
