Virtual Filesystem & .nsp Packages

The engine never cares where an asset comes from. Every runtime read goes through a virtual filesystem (VFS), so the exact same .nsd production runs from the development tree, a packaged .nsp file, or — later — an executable with an embedded package.

Why a VFS?

Engine subsystems used to open files directly (std::ifstream("data/shaders/foo.frag")). That bakes in "the file lives on disk next to the engine" — which breaks as soon as a production is distributed as a single file. The VFS answers one question: where are these bytes? The asset layer answers the other: what are these bytes?

architecturetext

Virtual path conventions

All runtime asset paths are production-relative virtual paths with / separators — never machine-specific absolute paths:

examplestext
shaders/tunnel.frag
data/scenes/intro.nsd
data/textures/noise.png
data/models/city.obj
data/materials/neon.json
data/post/nd_boot.json
data/shadertoy/tunnel_warp.glsl
assets/fonts/intro.ttf
data/neural_dust/track.mp3
  • On the development tree these map to shaders/, data/ and assets/ under the repo root.
  • In a package they resolve inside the .nsp — the packer writes the same virtual paths, so a production runs identically from either source.
  • Case and separator behavior follows the host OS: virtual paths are normalized to /; Windows hosts keep their usual case-insensitivity, other hosts are case-sensitive.

Usage

Development and packaged playback are the same binary — only the VFS mount differs, and it is selected once at startup:

terminalbash
# Development: run the dev tree directly (unchanged)
./build/Release/ns_demo.exe
./build/Release/ns_demo.exe --demo=data/demo.nsd
./build/Release/ns_demo.exe --editor

# Create a package from a production (discover all referenced assets)
./build/Release/ns_demo.exe --pack data/demo.nsd --output GhostInTheMachine.nsp

# Playback: mount the package as the VFS (no data/ directory needed)
./build/Release/ns_demo.exe --play GhostInTheMachine.nsp

Packaging runs headless — no window, no GL — so it works on CI. The production argument is resolved the same way the app resolves --demo, and an explicit --track=FILE is honored. --root=PATH points the packer at a repo root other than the current directory.

The .nsp package format

A deliberately simple custom format — no third-party dependencies, versioned for the future:

layouttext
Header    magic "NSPK" + format version + counts + data offset
Manifest  one entry per file: virtual path, offset, uncompressed size,
          compression method, FNV-1a hash
File data the bytes, back to back (uncompressed today; the method field
          leaves room for compression without breaking old packages)

The reader validates aggressively and fails safely:

  • bad magic / unsupported version → rejected up front
  • manifest smaller than the file table or past the end of the file → truncated package
  • entry offsets/sizes outside the file → rejected, never read
  • FNV-1a hash mismatch on read → corrupted data (FNV-1a is a lightweight integrity check, not a cryptographic hash — no security claims)

A hidden .ns-production entry records which production the package runs; --play uses it to pick the script automatically.

What the packer includes

The packer does not copy the whole data/ directory. It starts from the production script, parses it with the existing script engine, and collects every referenced asset:

  • shaders (every file under shaders/ — effects select shaders by name from code, so the whole set ships)
  • textures, models, materials (plus the albedo/normal maps materials reference)
  • post-processing presets, Shadertoy files, fonts (every TTF/OTF under assets/fonts/)
  • other .nsd scripts / scenes / timelines reachable from the production
  • audio: an explicit --track=FILE, else a soundtrack next to the script (its directory or the folder named after it, data/foo.nsd + data/foo/track.mp3) — sibling productions' tracks never leak in

Plugins are native libraries and cannot be loaded from inside a package — the packer warns and skips them (a documented limitation). The report lists every kind it found and the package size:

Where it lives in the code

The VFS is GL-free framework code — the renderer and shaders know nothing about packages:

layouttext
src/framework/vfs/
  vfs.hpp/.cpp          VirtualFileSystem interface, VFileInfo, path
                        normalization (rejects ../, absolute, drive letters),
                        runtimeFS() global the loaders use
  directoryfs.hpp/.cpp  DirectoryFileSystem: mounts virtual prefixes onto
                        real dirs ("data" -> repo/data, "" catch-all)
  nspack.hpp/.cpp       .nsp writer + reader (header, manifest, FNV-1a,
                        validation), PackageWriter for the packer
  packagefs.hpp/.cpp    PackageFileSystem: the reader behind the VFS API

src/app/packer.cpp      runProductionPacker: parses the .nsd, walks
                        references, writes the package, prints the report
src/main.cpp            --pack / --play / --root / --output parsing and the
                        one-time VFS selection near startup

Development/editor operations that must touch real files — saving, creating, watching, modifying production data — keep direct filesystem access; the VFS is the runtime read path. Hot reload and the editor are unchanged and remain dev-tree based.

Tests

The framework test suite (ns_fw_tests.exe) covers:

  • DirectoryFileSystem — existing/missing files, text & binary reads, path normalization, traversal rejection
  • Package format — create/read round trip, multiple files, empty file, binary file, large file, invalid header, invalid version, invalid offsets, truncated package, checksum failure
  • Equivalence — the same virtual paths resolve from the dev tree and from a package, with byte-identical contents
