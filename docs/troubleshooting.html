Troubleshooting

Everything fails loudly, by design — the engine logs the subsystem, the file and often the exact line to stderr. Here's how to read those logs and fix the common failure modes.

Reading the logs

All diagnostics go to stderr in a [TAG] message format. The tag names the subsystem:

TagSubsystemTypical messages
[MAIN]Shell / window / trackWindow creation, track fallback, app init failures
[PATHS]Runtime directory resolutionWhich dir a resource root resolved to, and why
[SHADER]Shader managerCompile errors, hot-reload results, include-depth warnings
[FX]Effect registry / pluginsRegistered effect count, plugin load failures
[AUDIO]Audio engineTrack decode, analyser, silent no-track mode
Tip

Run from a terminal — ./ns_demo.exe 2>&1 | tee show.log — so the log is on disk for post-mortems. The shipped data files parse cleanly, so if your edits break a load, the log names the file.

Shader compile errors

Compilation is strict and descriptive. A failed stage throws a std::runtime_error carrying the GLSL info log — including the offending line number — and the shader manager records it on the program state.

stderrlog
[SHADER] hot-reload failed for 'scene.frag' - keeping previous version:
compile error (scene.frag):
0(12) : error C1008: undefined variable "uTime"
IssueBehavior & fix
Syntax / type errorThe log names the stage, file and line. Fix the .frag/.vert and save — hot reload recompiles.
Undefined uniformNot an error. Reflection skips unknown uniforms, so a typo'd name silently does nothing. Check u* spellings against the shader.
#version 300 esRewritten to #version 330 core automatically. Don't add your own version line after the first.
precision highp float;Stripped automatically (desktop GLSL has no precision qualifiers).
Missing #includeRecorded as a missing dependency and the load fails — the log lists the include path. Files resolve relative to the shader dir.
Include cycle[SHADER] include depth exceeded at <file> (cycle?) after 16 levels.
Hot reload keeps old versionIntentional: a failed recompile keeps the previous working program live so the show never goes black mid-scene.

“undefined variable "Null"” — the include that silently vanished

The shared NullBlock UBO lives in shaders/common.glsl and is injected into every shader via #include <common>. If that include fails to resolve, the shader compiles without the UBO and every Null.u* read dies — a cryptic GLSL error that never names the real problem:

stderrlog
[MAIN] DemoApp init failed: shader compile failed (lit.vert + lit.frag):
compile error (lit.vert):
0(25) : error C1503: undefined variable "Null"

The historical cause: the app's shader manager built include paths without an extension, so #include <common> opened shaders/common (no .glsl) and silently vanished. Two things now make this impossible to miss:

  • Include resolution tries the literal name first, then appends .glsl — and any unresolvable file or include fails loudly with shader file not found: <path> (…, searched <dir>[, missing include]) instead of compiling an empty source.
  • The preflight catches it — --check-shaders also compiles the app's forward-lit lit.vert + lit.frag program, so a regression like this exits 1 at dev time instead of mid-show.
terminalbash
# healthy: engine stages + the app lit program all compile
[SHADER] engine preflight: 68/68 stages ok
[SHADER] app preflight: lit.vert + lit.frag ok

# regression (common.glsl missing): exit code 1, the file is named
[SHADER] app preflight failed: shader compile failed (lit.vert + lit.frag):
shader file not found: …/shaders/common.glsl (vert 'lit.vert', searched …/shaders, missing include)
Fix

Make sure common.glsl sits in the resolved shader dir (wherever NULLSECTOR_SHADER_DIR points — see path overrides), and that the include uses the exact name. Both #include <file> and #include "file.glsl" forms are supported; explicit extensions work too.

“I fixed my shader but it never hot-reloads” — the dead reload gate

You break a shader and save; the log warns. You fix it and save again — and nothing: no hot-reloaded line, ever, until you restart the app. The show never goes dark (it keeps the previous program) but your fix silently never applies.

The historical cause: pollHotReload() gated every program on an st->ok flag, and a failed recompile set it to false. One compile error therefore permanently disabled hot reload for that program — fixing the file changed nothing because the gate skipped it forever. Three behaviors surround this, and the log proves each:

  • “Keeping previous version” is intended, not the bug — compileProgram() only swaps the GL program on success, so a failed recompile leaves the previous working program bound and the show renders on. The [SHADER] hot-reload failed … - keeping previous version: warn is the proof.
  • Retry on the next change — the gate is gone; the fix re-runs whenever the file changes. On failure the program is marked permanently dirty (mtime = min), so even a timestamp-preserving restore (cp -p, git checkout, archive extraction) is retried.
  • 1-second retry throttle — a deleted shader file would otherwise fail + warn every poll (~60/s), because the dirty check short-circuits on the missing file before comparing mtimes. Attempts are capped at one per second.
stderrlog
# 1. you BREAK lit.frag mid-show - previous program stays live (never dark)
[WRN][SHADER] hot-reload failed for 'lit.vert + lit.frag' - keeping previous version:
compile error (lit.frag):
0(309) : error C0000: syntax error, unexpected identifier, expecting ',' or ';' at token "BADTOKEN"

# 2. you FIX lit.frag - the retry fires and swaps the program
[INF][SHADER] hot-reloaded 'lit.vert + lit.frag'
[INF][RELOAD] recompiled 1 shader program(s)

# 3. DELETED instead of edited: exactly ~1 warn/second (the throttle), not per-frame
[WRN][SHADER] hot-reload failed for 'lit.vert + lit.frag' - keeping previous version:
shader file not found: …/shaders/lit.frag (frag 'lit.frag', searched …/shaders)

# 4. file RESTORED: it comes back live
[INF][SHADER] hot-reloaded 'lit.vert + lit.frag'
Fix

If a hot-reload failed warn is followed by no hot-reloaded line after you save the corrected file, run ./ns_demo.exe --check-shaders to confirm the file compiles standalone, and verify it actually sits in the resolved shader dir (see path overrides). Current builds retry automatically — a missing retry means the manager isn't looking where your file is.

Shadertoy imports fail: “invalid string position” / “unexpected “==”” cascades

A Shadertoy file that should compile can fail in two cryptic ways — both from the pass-splitting step, not your GLSL:

stderrlog
# single-pass file whose header MENTIONS the marker text:
[ERR][SHADERTOY] pass '` markers = image pass).' failed:
0(21) : error C0000: syntax error, unexpected "==" at token "=="
0(33) : error C1503: undefined variable "p"
... (cascade: hash21 / fragCoord / fbm all "undefined")

# multi-pass file: the split arithmetic throws instead
[ERR][FX] effect 'shadertoy:tunnel_warp.glsl' init failed: invalid string position

Both symptoms are one bug in the pass parser. The marker scan matched // pass: anywhere, so a header comment like (no `// pass:` markers = image pass) or a nested // // pass: common - description became a false marker. Then the line-end arithmetic (markerPos + file.find('\n', markerPos) — adding an absolute offset to itself) truncated single-pass sources mid-comment — the bare ==== line is the unexpected "==" — and threw std::out_of_range (“invalid string position”) when the bogus start point landed past the next marker on multi-pass files. A third, separate bug dropped the common pass entirely and re-ordered passes by moving out of the container mid-iteration, leaving phantom empty passes (pass '' failed: … no program defined). All three are fixed; the rules are now:

  • A marker is a line whose first comment is pass:, with only whitespace before it, and the name is a single token — prose mentions and nested comments never split a file (see the Shadertoy page).
  • The common pass is prepended to every other pass, so shared helpers (hash21, warp, …) are in scope for buffer and image passes.
  • Pass re-ordering copies instead of moving out of the container, so no phantom empty passes remain.
Fix

Make sure marker lines are standalone (// pass: image alone on its line) and that your file's header doesn't literally echo the marker text. The shipped plasma.glsl and tunnel_warp.glsl split into 1 and 3 passes respectively — ns_fw_tests verifies the split GL-free, so a future parser regression fails there before it reaches a show.

This exact log also identifies a stale binary. The two signatures above — pass '` markers = image pass).' and init failed: invalid string position — are the old parser's fingerprints, and no build newer than the fix can produce them: the strict rule rejects prose mentions outright, and the splitter's line-end arithmetic no longer throws. If they appear after a rebuild, the running exe is pre-fix — an old ns_demo.exe shadowing the new one on PATH or in the working directory, a different copy launched from a file manager, or a stale build output. Prove the build in two seconds:

terminalbash
# a CURRENT binary compiles every data/shadertoy file and exits 0:
./ns_demo.exe --check-shadertoy
[INF][SHADERTOY-CHECK] ok: plasma.glsl compiles + links
[INF][SHADERTOY-CHECK] ok: tunnel_warp.glsl compiles + links
[SHADERTOY] preflight: 7/7 checks ok          # RC 0 - parser is current, look elsewhere

# ... while the OLD binary repeats the mystery log even on the same files:
[ERR][SHADERTOY] pass '` markers = image pass).' failed:
[ERR][FX] effect 'shadertoy:tunnel_warp.glsl' init failed: invalid string position
Stale binary?

Before debugging your GLSL, run ./ns_demo.exe --check-shadertoy. RC 0 with preflight: 7/7 checks ok means the parser in the running binary is current — the error is in your data, the log names the file, or the log is simply from an old run. If the check itself reproduces the failure, that's a code regression worth reporting — it can't silently reach a show.

Multi-pass Shadertoy shows a solid colour / black (single-pass files fine)

A multi-pass shadertoy (e.g. tunnel_warp.glsl, which has // pass: buffer_a + // pass: image) can compile cleanly yet render as one flat colour — while single-pass files (plasma.glsl) are fine. The importer's buffer loop binds its own RGBA16F targets, and the image pass then drew into whatever framebuffer was still bound — the last buffer — instead of the caller's scene target, and it sampled that same buffer (and the scene) while doing so. Sampling a texture that is attached to the very framebuffer you are drawing into is undefined behaviour; on most drivers it collapses to a solid colour or black, and the composite never reached the screen.

The fix has two halves:

  • The scene is snapshotted once up front — the live scene (ctx.hdr) is copied into an internal target before any pass runs, and iChannel1 (the “live scene” input) plus buffer A's fallback sample that copy. Nothing ever samples the target being written.
  • The image pass rebinds the caller's scene target before drawing, so the final composite lands where the post pipeline reads it — not in the last buffer.
Fix

This class of bug is now caught before the show: ./ns_demo.exe --check-shadertoy renders every data/shadertoy/*.glsl offscreen and verifies the frame both reaches the scene target (not stuck at the clear colour) and has spatial variance (not a feedback-loop solid). A regression in the pass pipeline fails there with the offending file named, instead of mid-scene.

Validate

./ns_demo.exe --check-shaders compiles every engine shader stage plus the app's forward-lit lit program and exits — use it in CI to catch shader regressions before they reach a show. Data-referenced shaders compile when their effect first shows.

Missing track → silent show

There is no built-in synthesizer anymore — the engine only plays real WAV/MP3 files. If it can't find a track the show runs silently: the audio device stays closed, the FFT/beat visuals have nothing to react to (the analyser reads zero), and the timeline still advances on the wall clock so the show never freezes.

stderrlog
[MAIN] no WAV/MP3 track found - the show will run silent (no built-in synth)
[AUDIO] no track file - running silent (drop a WAV/MP3 to add music)

The shell searches, in order: the --track=FILE override, then common names in the current directory and the executable's directory — ghostinthemachine.mp3, audio.mp3, assets/audio.mp3, and the .wav variants.

FixCommand
Point at a specific file./ns_demo.exe --track=music/ghost.mp3
Drop a track beside the exeName it audio.mp3 or ghostinthemachine.wav
Run deliberately silent./ns_demo.exe --no-track
Verify decode headlessly./ns_demo.exe --smoke-audio --track=music.mp3
Tip

Decode failures for a found file (corrupt or unsupported format) keep the previous source — silence if none was playing — and the audio engine logs the reason. WAV (16/24-bit) and MP3 are the battle-tested formats.

GLFW fetch failures at configure

The build system first looks for a system GLFW (find_package(glfw3)). If none exists, CMake fetches GLFW 3.4 from GitHub at configure time — which needs network access.

terminalbash
cmake -S . -B build -DNS_BUILD_APP=ON   # fetches GLFW from github.com
# fails with a network error when GitHub is unreachable
FixHow
Work offline (framework only)cmake -S . -B build -DNS_BUILD_APP=OFF — no GLFW needed for the framework + tests.
Install system GLFWapt install libglfw3-dev (Linux) or brew install glfw (macOS); find_package then skips the fetch.
Pre-seed the cacheLet a networked machine configure once; the downloaded GLFW sources cache in CMake's download dir and reuse on later configures.
Check proxy / mirrorsThe fetch URL is https://github.com/glfw/glfw/archive/refs/tags/3.4.tar.gz — corporate proxies or blocked hosts need a mirror or a vendored glfw3.
Window won't open

A different failure: [MAIN] window creation failed at runtime means the GL context couldn't be created — the engine wants OpenGL 3.3 core. Update GPU drivers, or check for remote-desktop/VMs that expose only older GL.

Plugin load failures

Plugins are shared libraries (.dll / .so) loaded from data/plugins/ (or --plugin=DIR). Loading is best-effort: a bad plugin logs and continues — it never takes the show down.

stderrlog
[FX] plugin load failed (dlopen): data/plugins/stars.so - cannot open shared object file
[FX] plugin 'data/plugins/stars.dll' does not export ns_register_plugins()
MessageCause & fix
plugin load failed (LoadLibrary / dlopen)The OS refused the library — usually an architecture mismatch (plugin must match the exe: 64-bit exe → 64-bit plugin), a missing dependent DLL, or a missing file. dlopen appends dlerror(), which names the reason.
does not export ns_register_plugins()The library loaded but lacks the entry point. Export exactly extern "C" void ns_register_plugins() and don't mangle it (no namespace wrapper, no C++ name mangling).
Plugin loads, effects missingThe entry point must call ns::registerEffect(...) for each effect before it returns. Verify with [FX] plugin loaded: … (N effects registered) — the count tells you if anything registered.
Plugin not scanned at allCheck the plugin dir exists and is passed: default is data/plugins/; override with --plugin=DIR.

Path overrides & the NULLSECTOR_*_DIR variables

The binary bakes the build machine's absolute source paths in at compile time. That breaks a packaged folder (exe + shaders/ + data/) copied to another machine — every shader load fails and the demo degrades. So each runtime directory resolves by walking candidates in order:

resolution order (highest first)logic
1. env override       NULLSECTOR_*_DIR         exact, highest priority
2. baked build path   NULLSECTOR_*_DIR define   only if it still exists
3. exe directory      <exe-dir>/<name>          packaged folder: resources beside the exe
4. working directory  ./<name>                  dev runs from the repo root
→ falls back to the baked path when nothing exists,
  so error messages still point at the build-time location
Env varResource root it controls
NULLSECTOR_SHADER_DIRWhere shaders/*.glsl are found (src/engine/paths.hpp).
NULLSECTOR_ASSET_DIRWhere assets/* (textures, fonts) are found.
NULLSECTOR_DATA_DIRWhere data/ (demo.nsd, post/, models/…) is found.
terminalbash
# packaged run: everything beside the exe, no source tree needed
export NULLSECTOR_SHADER_DIR=/opt/show/shaders
export NULLSECTOR_ASSET_DIR=/opt/show/assets
export NULLSECTOR_DATA_DIR=/opt/show/data
./ns_demo.exe --windowed

When a fallback kicks in, a one-line notice explains what happened:

stderrlog
[PATHS] 'shaders' resolved to '/opt/show/shaders' (baked 'C:/src/NS_DemoEngine/shaders' not present)
SIGNAL LOST

If every shader fails to load, the demo degrades to "SIGNAL LOST" placeholder screens — that's the intended canary for a broken shader dir. Setting NULLSECTOR_SHADER_DIR (or placing shaders/ beside the exe) fixes it.

Diagnostic checklist

When in doubt, run the shipped validations — they isolate engine, data and audio independently:

terminalbash
./build/Release/ns_fw_tests.exe            # framework + data-file parsing + live-reload chain (253 checks)
./build/Release/ns_demo.exe --check-shaders # every engine stage + app lit program compile
./build/Release/ns_demo.exe --check-models  # 3D pipeline: OBJ -> lit shader -> draw readback
./build/Release/ns_demo.exe --check-hotreload --no-track  # live-reload smoke: keep-previous + recompile
./build/Release/ns_demo.exe --check-shadertoy  # shadertoy pass pipeline: render + readback
./build/Release/ns_demo.exe --smoke-audio --track=music.mp3  # track decode + analyser
  • Tests pass but the show breaks → your data is at fault; the log names the file.
  • --check-shaders fails → the code regressed (an engine or app shader); that's a code issue, not data.
  • --check-models fails → the 3D pipeline regressed (OBJ import, lit shader, material, or a shipped model/material file).
  • --check-hotreload fails → hot reload regressed (a failed reload no longer keeps the previous program, or the retry no longer recompiles after a fix).
  • --check-shadertoy fails → the Shadertoy pass pipeline regressed (the image pass isn't reaching the scene target, or a feedback loop goes solid).
  • --smoke-audio fails → the track file, not the engine.
